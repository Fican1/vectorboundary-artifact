The convergence of Large Language Models (LLMs) and the open-source RISC-V architecture creates signif-
icant opportunities for specialized AI hardware. However, achieving optimal LLM inference performance
on RISC-V platforms is challenging due to the complex computational patterns of LLM operators and the
architectural nuances of the RISC-V Vector (RVV) extension. Existing optimization strategies often rely on
manual, expert-driven tuning, which is labor-intensive and not generalizable across diverse operators and
hardware configurations. This article presents VectorWeaver, an automated framework to generate high-
performance, stage-aware microkernels for LLM inference on RISC-V. VectorWeaver specifically addresses
key performance bottlenecks in quantized models, such as memory discontinuities in vector dot-product
operations, by employing a widen vectorization strategy. Guided by a stage-aware performance model, the
framework systematically explores a rich optimization space encompassing loop unrolling, software pipelining,
and mathematical approximations. The model generates distinct, highly-optimized kernels for the prefill and
decode stages, selected at runtime via a dispatch mechanism. We evaluate VectorWeaver on the TH1520
and the Sophon SG2044 using Gemma3 and Qwen3 models with sizes ranging from 270M to 4B, where our
generated microkernels achieve up to a 24x speedup over baseline implementations. For end-to-end evalua-
tions, VectorWeaver delivers up to a 5.2x increase in inference throughput, demonstrating its effectiveness in
automating the generation of high-performance code and advancing the state of LLM inference on the RISC-V
ecosystem.

Introduction
Large Language Models (LLMs) have become a dominant force in modern computing [35], yet
their massive computational and memory requirements pose significant challenges for deployment
on resource-constrained edge devices [46]. This challenge marks a critical inflection point in the
evolution of artificial intelligence, often termed the shift from “Cloud AI” to “Edge AI” [41]. This
paradigm shift is driven by burgeoning demands for real-time responsiveness, enhanced data
privacy, and reduced operational costs, all of which are difficult to achieve when relying solely on
remote data centers. The proliferation of intelligent applications in autonomous vehicles, smart
homes, and personal robotics further necessitates powerful, on-device processing capabilities [26].
Concurrently, the RISC-V architecture is gaining momentum as a flexible, open-standard alter-
native to proprietary CPUs [34], particularly in the embedded and custom hardware space. Its
modular, extensible nature makes it an ideal substrate for creating domain-specific accelerators
(DSAs) tailored for AI workloads. The RISC-V Vector (RVV) extension, in particular, provides a
powerful and adaptable mechanism for data-parallel computation, making it a promising target for
accelerating the dense linear algebra operations at the heart of LLM workloads [5].
However, bridging the gap between high-level LLM frameworks like llama.cpp [16] and high-
performance RVV assembly is non-trivial [18]. Achieving optimal performance is not merely a
matter of straightforward code compilation; it is a multi-faceted problem fraught with challenges
that lie at the intersection of algorithm, software, and hardware architecture [17].
We identify four primary hurdles that complicate this landscape. First, the ecosystem suffers
from architectural fragmentation due to the intentionally flexible RVV specification, which allows
implementers to choose different vector lengths (VLEN) and pipeline designs [11]. Consequently,
an optimization strategy effective on one core may be suboptimal on another, demanding a portable
methodology. Second, this hardware variability is compounded by operator complexity. The perfor-
mance of key operators, particularly quantized matrix multiplication and activation functions, is
highly sensitive to data layout and instruction scheduling [1], where subtle issues like memory
discontinuities in quantization schemes can cripple naive vectorization. Third, the workload itself
exhibits a prefill-decode dichotomy. LLM inference is not monolithic but comprises two distinct
phases: the parallel, compute-bound “Prefill” stage and the sequential, memory-bound “Decode”
stage [21, 48]. A truly effective framework must be “stage-aware,” as a single, statically optimized
kernel is unlikely to suffice for both. Finally, these challenges collectively create a manual optimiza-
tion bottleneck. Current state-of-the-art solutions rely on labor-intensive, expert-driven tuning that
is inherently fragile–failing to scale to new operators, evolving architectures, or next-generation
hardware.
To address these challenges, we propose VectorWeaver, an automated framework designed to
generate highly optimized, stage-aware microkernels for LLM inference on RISC-V platforms.
VectorWeaver automates the entire optimization workflow, from high-level operator definitions to
the synthesis of fine-tuned RVV assembly code, making principled, architecture-aware decisions to
navigate the complex optimization space.

— Novel RISC-V Microkernel Optimizations: We introduce a “Width Expansion” strategy
that reorganizes in-register data to overcome memory access bottlenecks in quantized

2
Background and Motivation
2.1
RISC-V Vector Extension (RVV)
The RVV extension enhances RISC-V with a flexible and powerful SIMD paradigm. Unlike more
rigid SIMD architectures, RVV is designed to be highly configurable [19]. Its key concepts include:
— Vector Registers: A set of 32 vector registers (v0-v31). The physical length of these registers,
VLEN, is implementation-defined (e.g., 128, 256, 512 bits).
— Dynamic Configuration: The vsetvli instruction is central to RVV’s flexibility. It con-
figures the vector unit at runtime, setting the standard element width (SEW) and the vector
register grouping multiplier (LMUL). SEW can be 8, 16, 32, or 64 bits. LMUL (1, 2, 4, 8) allows
multiple physical vector registers to be aggregated into a single, wider logical vector register.
This provides a powerful mechanism for fine-grained control over data layout in registers, a
capability we exploit in our work.
— Masking and Predication: Most vector instructions can be masked, allowing operations to
be selectively applied to elements based on the value in a special mask register (v0), enabling
efficient handling of conditional logic and irregular data structures without branching.
— Memory Access: RVV supports a rich set of memory access patterns, including unit-stride
(ideal for contiguous arrays), strided (for accessing columns in a row-major matrix), and
indexed (for gather/scatter operations). This versatility is essential for complex algorithms
but also complicates the task of optimization.
This inherent flexibility is a double-edged sword: while it offers immense potential for performance
tuning, it also creates a vast optimization space that is challenging for traditional compilers to
navigate effectively. Manual optimization requires deep expertise in both the algorithm and the
specific RVV implementation.

— Decode: New tokens are generated auto-regressively, one at a time. Each new token
requires a full pass through the model’s layers. This phase is characterized by matrix-vector

2.3
Profiling and Bottlenecks in llama.cpp on RISC-V
To motivate our work, we profiled the widely-used “llama.cpp” framework on a RISC-V platform.
A key bottleneck emerged in the quantized vector dot-product function (“ggml_vec_dot_q8_0”),
which is fundamental to all matrix multiplications. The Q8_0 quantization format stores 32 8-bit
integers (int8_t) along with a 16-bit floating-point scaling factor (ggml_half) for each block, as
shown in Figure 2(a, b).
A direct vectorization of the dot product between two such blocks is inefficient. As illustrated in
Figure 2(c), the 32 integer values can be loaded into a vector register, but the single scaling factor
must be loaded separately into a scalar register and then broadcasted to another vector register
before the final multiplication. This creates a long data dependency chain: the vector multiplication
cannot begin until the scalar load and broadcast are complete. This serialization breaks the data flow,
stalls the pipeline, and leads to a severe underutilization of the vector ALUs. The core issue is the
memory discontinuity imposed by the quantization format, which prevents a simple, contiguous
load of all necessary data for a fused multiply-add operation, thereby crippling SIMD throughput.

unique flexibility of the RVV architecture.

3.1
Exploiting RVV’s Flexible Data Layout
The core of our optimization philosophy lies in leveraging RVV’s configurable vector registers. As
shown in Figure 3, by adjusting the LMUL parameter via the vsetvli instruction, a programmer
can treat a group of physical vector registers as a single, wider logical entity. For instance, with
VLEN=128b and SEW=8b, a standard vector register v0 holds 16 elements. By setting LMUL=2, registers
v0 and v1 are concatenated to form a logical register that can hold 32 8-bit elements. Setting LMUL=4
concatenates v0-v3. This capability for fine-grained, in-register data arrangement provides a
powerful tool to restructure data layouts post-load, enabling optimizations that are impossible in
more rigid SIMD architectures.

3.3
Loop Unrolling and Software Pipelining
To maximize Instruction-Level Parallelism (ILP) [37], VectorWeaver systematically applies loop
unrolling. By increasing the number of independent instructions in the loop body, we provide the
processor’s pipeline with more opportunities for parallel execution [4], which is critical for hiding
the latency of both floating-point operations and memory accesses. This is particularly effective on
superscalar RISC-V cores.
VectorWeaver implements this using inline RVV assembly, giving it fine-grained control over
instruction scheduling. It parameterizes the unroll factor and generates code that explicitly inter-
leaves load, compute, and store instructions from different logical loop iterations. This manual
software pipelining is crucial for achieving performance close to the hardware’s peak, as it can
explicitly manage data dependencies and prevent pipeline stalls from memory operations, a task
where compilers often struggle [39]. The tradeoff is increased code size and register pressure, which
our performance model must account for.
3.4
Mathematical Approximation
Certain activation functions, like SiLU (Sigmoid-weighted Linear Unit), are computationally expen-
sive. The function, defined as 𝑆𝑖𝐿𝑈(𝑥) = 𝑥⋅𝜎(𝑥) = 𝑥/(1 + 𝑒−𝑥), involves the exponential function
𝑒𝑥, which is not a native RVV instruction and typically requires a slow, non-vectorized library call.
VectorWeaver incorporates a strategy for mathematical approximation to overcome this
bottleneck. Instead of relying on generic library routines, it expands its search space to include
fast, vectorized approximations. For the exponential function, one highly effective technique
is a hardware-friendly variant based on direct manipulation of the IEEE 754 floating-point

It allows this strategy to be selectively enabled, providing a “knob” to tune for either maximum
speed or full model accuracy. Our evaluation in Section 5 quantifies this tradeoff, showing that for
many models, a slight approximation yields significant speedup with negligible impact on output
perplexity.
These strategies–Width Expansion, Loop Unrolling, and Mathematical Approximation–are not
mutually exclusive. VectorWeaver’s core strength lies in its ability to combine them. For a given
operator, it can generate multiple candidate kernels, each representing a different combination of
these techniques (e.g., a width-expanded kernel with an unroll factor of 4). The framework’s role,
described next, is to automate the search for the best combination.
4
VectorWeaver: Automated RISC-V Microkernel Optimization
4.1
Automated Optimization Workflow
The optimization of LLM kernels on modern RISC-V platforms presents a formidable challenge,
characterized by a vast and complex optimization space that spans instruction selection, data
layout, and loop transformations. Manual optimization in this domain is not only a labor-intensive
endeavor requiring deep architectural expertise but is also inherently fragile, as solutions are tightly
coupled to a specific hardware implementation. VectorWeaver is conceived as a systematic solution
to this problem, replacing ad-hoc, expert-driven tuning with a principled, automated workflow that
robustly navigates this complexity. The framework’s workflow, depicted in Figure 5, orchestrates
a seamless progression from a high-level, abstract kernel definition to the synthesis of multiple,
highly-specialized, and hardware-specific assembly codes.
The process is initiated in the IR Generation stage. Here, a user-provided kernel, expressed in a
high-level C-like syntax, is lowered into our custom VA-IR. This initial VA-IR instance captures the
pure, unoptimized semantics of the operation. Subsequently, this representation is passed to the
Adaptive Strategy Exploration stage, the core of the framework. The Weaver-Optimizer engine
systematically applies a library of predefined transformation strategies to the VA-IR. This is not a
single-pass transformation; instead, it generates a diverse population of distinct VA-IR instances,
where each instance is a unique candidate kernel defined by a specific combination of optimizations
(e.g., Width Expansion with an unroll factor of 4, versus a naive approach with an unroll factor of 2).
This population of candidates is then fed into the Performance Model Feedback stage. This stage

4.2
Core Components: VA-IR and Performance-Guided Search
The efficacy and automation capabilities of the VectorWeaver framework are underpinned by
two core technical components: its domain-specific intermediate representation designed for
architectural modeling, and its intelligent, search-guiding performance model.
The Vector-Adaptive Intermediate Representation (VA-IR) serves as the central data struc-
ture and the primary abstraction layer within the framework. Its design is a direct response to
the limitations of general-purpose compiler IRs like LLVM IR [42, 45], which are fundamentally
target-agnostic. The VA-IR, by contrast, is intentionally target-aware, providing a parametric model
of the RVV architecture’s configurable features. Unlike SSA-based representations that focus on
data flow analysis, VA-IR adopts a kernel-centric design that explicitly decouples computation
semantics from optimization decisions, enabling the systematic exploration of the RVV optimization
space.
A VA-IR program is structured around three core abstractions. The KernelIR component defines
the overall kernel structure, including loop bounds, input/output ports with type annotations, and a
sequence of named computation stages. Each stage encapsulates a logically coherent operation phase

within the loop body, such as data loading, arithmetic computation, or reduction. Between stages,
VA-IR supports embedding C++ code fragments—termed interludes—to handle non-vectorizable
operations like scale factor computation in quantized kernels. This multi-stage design naturally
captures the structure of complex LLM operators that interleave vector and scalar operations.
Within each stage, the computation is expressed through IROperations—primitive vector opera-
tions that abstract RVV instruction semantics. These operations span five categories: memory oper-
ations (load, store) for vector data movement; data extraction operations (unpack_lo, unpack_hi)
for nibble and byte manipulation in quantized formats; compute operations (vwmul, vwmacc, vfmul)
covering widening multiply, fused multiply-accumulate, and floating-point arithmetic; reduction
operations (vwredsum, vfredosum) for vector-to-scalar aggregation; and conversion operations
(vfcvt, vnsrl) for type transformations. Crucially, IROperations do not prescribe specific register
allocations or instruction encodings; instead, they declare the semantic intent, allowing the code
generator to make target-specific decisions during synthesis.
The third abstraction, TuningConfig, encodes the optimization parameters that collectively
define the search space for auto-tuning. These parameters are organized into four categories that
reflect distinct optimization concerns. Code generation level determines whether the output targets
portable RVV intrinsics or hand-optimized inline assembly for maximum control. Loop optimization
parameters include unroll factor, which specifies how many loop iterations are processed together;
pipeline style, which controls whether unrolled iterations execute in a serial load-compute-store
pattern or an interleaved pattern that overlaps memory and compute operations; and block batch
size for processing multiple quantization blocks per iteration. RVV-specific parameters capture
architectural decisions unique to vector processors: LMUL strategy selects between full width (e.g.,
LMUL=m2 processing 32 elements) or split mode (LMUL=m1 processing 2×16 elements with explicit
halving); instruction fusion enables combining separate widening multiply and add operations
into a single vwmacc instruction; and widening mode controls the use of widening operations for
precision preservation. Finally, precision and approximation control governs numerical tradeoffs:
accumulator strategy selects f32 or f64 precision for numerical stability in reduction-heavy kernels,
while mathematical approximation options enable fast implementations of transcendental functions.
The key insight underlying VA-IR’s design is that the same kernel description, when combined
with different TuningConfig instantiations, yields fundamentally different code variants—each
optimized for a specific hardware context or execution phase. This transforms the optimization
task from opaque code generation into a well-defined search problem over the VA-IR’s parameter
space, effectively enabling the optimizer to perform a “what-if” analysis for myriad optimization
combinations before any code is generated. Figure 6 illustrates this mapping: the IROperations
in a kernel definition (Figure 6(a)) are lowered to RVV assembly sequences (Figure 6(b)) through
template instantiation, with the specific code structure determined by the TuningConfig parameters
(Figure 6(c)).
The Performance-Guided Search intelligently navigates this vast parameter space using
a stage-aware machine learning model. We employ an XGBoost model specifically configured
for a learning-to-rank task, a paradigm chosen for its robustness against the inherent noise and
variability of physical hardware measurements. A model that predicts relative performance ranks
is less susceptible to being misled by transient system effects than one predicting absolute latency.
The model’s predictive power is derived from a meticulous feature engineering process. We extract
a rich feature vector from each VA-IR candidate, including: (1) Static Code Features like the ratio
of ALU operations to memory accesses, the complexity of loop-carried dependencies, the degree
of ILP, and an analytical estimate of register pressure; and (2) Contextual Features such as the
input sequence length and a crucial binary flag, is_prefill. The model is trained offline on a
dataset collected by benchmarking a curated, representative subset of kernel configurations on the

Decode stage is memory-bound and latency-sensitive. Our experiments on the SG2044 platform
reveal that this distinction is not merely a matter of tuning parameters but requires fundamentally
divergent architectural approaches. As illustrated in Figure 7, blindly applying throughput-oriented
optimizations to the Decode phase can lead to catastrophic performance degradation.
We identify three primary sources of overhead that make Prefill-optimized kernels detrimental
to the Decode stage, particularly on newer RISC-V implementations like the SG2044:
— Configuration Latency (vsetvli): Prefill kernels, such as those employing our Width
Expansion strategy, frequently toggle the vector register grouping (LMUL) to maximize Arith-
metic Logic Unit (ALU) utilization. In the Decode stage, where the problem size is small
(often a single token), the cycle cost of these vsetvli instructions becomes a significant
percentage of the total execution time, negating any arithmetic gains.
— Tail Loop Dominance: Aggressive widening and unrolling require large multiples of data
elements. When processing small batches in the Decode stage, the majority of the data often
falls into the scalar “tail loop” rather than the vectorized main loop, forcing the CPU into a
slower execution path.
— Granularity Mismatch: On hardware where the physical vector length (VLEN) is limited
(e.g., 128 bits), a standard quantization block (32 × int8) exceeds a single register’s capacity.
While Prefill kernels can mask the cost of loading and widening this data across many
iterations, Decode kernels suffer from the overhead of managing these splits dynamically.

To address these challenges, VectorWeaver employs a dual-surface learning approach. During
synthesis, the performance model is queried with distinct context flags (is_prefill) for each
operator. For the Prefill stage, the model selects kernels utilizing Maximum Width Expansion and
deep software pipelining (Figure 7, top), as the massive data volume successfully amortizes the
instruction overhead. However, for the Decode stage, the framework shifts to a “latency-minimalist”
strategy (Figure 7, right). Instead of widening vectors dynamically, VectorWeaver generates kernels
that maintain a static configuration (typically LMUL=1) throughout the function’s lifespan. This
involves techniques such as splitting input data across multiple registers during the load phase
to fit fixed register widths, thereby eliminating the need for mid-kernel vsetvli reconfigurations
and minimizing register pressure. This approach also reduces the overhead often introduced by
standard intrinsics, favoring lean, inline assembly sequences.
This automated decision-making is materialized via a lightweight runtime dispatcher. Inte-
grated into the inference loop, this dispatcher directs program flow based on token count with
negligible overhead. This mechanism effectively resolves the “performance seesaw” observed in
static optimization strategies–where optimizing for one stage penalizes the other. As we will
demonstrate in Section 5 (specifically the ablation study in Figure 7), VectorWeaver’s ability to
dispatch the optimal kernel for each phase allows it to match the peak throughput of specialized
static baselines (PP-Best and TG-Best) simultaneously, without compromising either.

5.4
Ablation Study on Stage-Aware Optimization
A central hypothesis of our work is that the divergent computational characteristics of the Prefill and
Decode stages necessitate specialized microkernels. To quantitatively validate this, we conducted
a targeted ablation study comparing our full dynamic framework against the static PP-Best and
TG-Best configurations.
As illustrated in Figure 10, the experimental outcomes strongly corroborate our hypothesis,
exposing the significant performance tradeoffs inherent in static “one-size-fits-all” optimization
strategies. This tradeoff is particularly pronounced on the high-performance SG2044 platform.
For instance, with the Qwen-0.6B model on SG2044: The PP-Best configuration achieves a high
prefill throughput of 227.2 tok/s but suffers drastically in the decoding phase, only achieves 24.4
tok/s–significantly lower than TG-Best’s 54.1 tok/s due to the overhead of managing large tile sizes
in a memory-bandwidth-limited context.
A similar trend is observed on the resource-constrained TH1520 platform. For the Gemma-4B
model, TG-Best provides the optimal decoding speed (0.88 tok/s) but lags in prefill (1.46 tok/s)
compared with PP-Best (1.93 tok/s). These disparities highlight that no single static kernel can
optimally serve both phases.
VectorWeaver successfully navigates this dilemma through its stage-aware dispatch mechanism.
By dynamically selecting the optimal kernel for each phase, it consistently matches the best-in-class
performance for both stages. On the SG2044 (Qwen-0.6B), VectorWeaver achieves 226.1 tok/s in
prefill and 54.1 tok/s in decoding, effectively mirroring the peak performance of PP-Best and
TG-Best respectively, with negligible runtime overhead.
This ablation study provides empirical evidence that stage-aware optimization is essential for
RISC-V LLM inference. The performance gap between static strategies widens as hardware paral-
lelism increases (as seen on SG2044), making the dynamic dispatch mechanism of VectorWeaver
not merely beneficial, but critical for maximizing hardware utilization across the entire inference
lifecycle.

5.6
Discussion
The comprehensive evaluation of VectorWeaver provides a multi-faceted validation of its core
design principles and reveals critical insights into the optimization of LLM inference on RISC-V
architectures. The empirical results, spanning micro-benchmarks, end-to-end throughput, scalability,
and targeted ablation studies across both the TH1520 and SG2044 platforms, collectively build a
compelling case for an automated, architecture-aware, and stage-specific approach. The significant
performance gains are not the result of a single optimization, but rather the synergistic effect of
the framework’s hierarchical methodology.
A foundational takeaway from our micro-benchmark analysis is the profound inadequacy of
general-purpose optimization heuristics for highly specialized workloads like quantized LLM infer-
ence. The dramatic speedups observed in our “Vec-Dot” kernels–reaching up to 6.89× on SG2044 via
the Width Expansion strategy–and in the “Vec-SiLU” function (up to 24.82×) through mathematical
approximation, underscore the necessity of domain-specific knowledge. These transformations
address subtle data-layout and computational bottlenecks that lie beyond the semantic reach of
a standard compiler, which often fails to produce meaningful vectorization for quantized types.
This motivates VectorWeaver’s multi-level code generation capability. While the automated search
over RVV intrinsics delivers substantial gains, the ability to generate direct, fine-tuned assembly
unlocks the hardware’s theoretical peak throughput. For instance, on the SG2044 platform, the
assembly-optimized SiLU kernel reduces latency to 2.48 𝜇𝑠, significantly outperforming the intrinsic
version (4.46 𝜇𝑠).
The empirical validation of our stage-aware architectural thesis is conclusive. The ablation study
demonstrates that a “one-size-fits-all” kernel strategy is fundamentally flawed, particularly as
hardware parallelism increases. On the 64-core SG2044, the static “PP-Best” configuration achieves
high prefill throughput but suffers catastrophic performance degradation in the decoding phase
due to synchronization and configuration overheads. Conversely, “TG-Best” excels at low-latency

mechanism successfully resolves this conflict, matching the peak performance of each specialized
configuration without manual intervention. This result elevates stage-aware design from a heuristic
improvement to a foundational requirement for high-performance RISC-V LLM inference.
Necessity of the Performance Model. Our experiments further highlight the critical role
of the Performance Model in the optimization loop, driven by two key factors: validation cost
and performance non-linearity. First, direct on-device validation in edge scenarios is prohibitively
expensive. Cross-compilation environments separate build and execution, and rigorous end-to-end
testing is time-consuming–for instance, a full perplexity (PPL) test for a 0.6B model using a scalar
baseline on the TH1520 platform requires approximately 32 hours. This necessitates a reliable
proxy model to rank candidates offline. Second, operator-level speedups do not linearly translate to
end-to-end gains across different model scales. Our evaluation on the SG2044 reveals a complex
behavior: while intrinsic-based optimizations provide gains for smaller models (e.g., Qwen3-0.6B
and Gemma3-270m), they often degrade performance compared with scalar implementations in
the Decode phase for larger models or other configurations. This counter-intuitive phenomenon
suggests that instruction overheads and cache behaviors vary significantly with model size, making
manual heuristic selection unreliable. Our performance model, trained on SG2044 data, achieves an
average ranking accuracy of 75% when transferred to TH1520 tasks, demonstrating high utility as
a robust filter against performance regressions. Crucially, the model allows us to identify platform-
specific constraints, effectively pruning configurations that exceed the 32-register limit to prevent
performance degradation caused by register spilling. This is particularly critical given the non-linear
relationship observed between operator efficiency and model scale: on the SG2044, while intrinsic-
based optimizations benefit smaller models, they often counter-intuitively degrade performance
for larger models due to complex cache interactions.
Future Work. We observed a significant disparity in optimization efficacy across different
model sizes, where the same kernel implementation behaves differently on 0.6B versus 4B models.
This phenomenon presents an intriguing avenue for future research. These findings suggest that
the interplay between micro-kernel instruction scheduling and macroscopic model architectural
hyperparameters (e.g., hidden size, head count) is more tightly coupled than typically assumed.
Furthermore, while our framework demonstrates adaptability across two distinct microarchitectures
(SG2044 and TH1520), future work is needed to address zero-shot generalization across wider
architectural variations, such as different VLEN configurations. While VectorWeaver currently
addresses this via search, these insights indicate that future optimization frameworks for RISC-V
may need to evolve from purely operator-centric views to more holistic, model-structure-aware
cost functions to fully exploit hardware potential across varying scales.
6
Related Work
Our research is situated at the intersection of LLM inference optimization and automated code
generation for novel hardware architectures. We survey the most relevant work in both domains.
6.1
LLM Inference Acceleration on CPUs
The pursuit of efficient LLM inference has spurred a wide range of optimization techniques. At a
high level, methods like speculative decoding [24] and modifications to the attention mechanism,
such as FlashAttention [13] and its variants [12, 40], aim at reducing the overall computational
volume, though they are primarily designed and optimized for GPUs’ massively parallel architecture.
Other orthogonal approaches focus on reducing the memory footprint and bandwidth requirements
of the Key-Value (KV) cache [29], a primary bottleneck in the memory-bound decode stage,
through techniques like compression and specialized data structures [2, 8, 15, 27, 28, 30].

Model quantization [22] has emerged as a critical strategy for deploying LLMs on resource-
constrained devices, reducing model size and enabling faster integer-based computations. This is
the area most adjacent to our work. While significant research has focused on quantization-aware
training and post-training quantization to minimize accuracy loss, the challenge of generating
high-performance kernels for these quantized data types on CPUs remains [9]. Most low-level
CPU optimization work, exemplified by libraries like ggml in llama.cpp, has concentrated on
architectures with established SIMD instruction sets [31], such as x86 (AVX) and ARM (NEON).
RVV supports variable-length logical vector registers (via LMUL) critical for quantized kernels, a
capability which AVX lacks. VectorWeaver distinguishes itself by being, to our knowledge, the first
automated framework specifically designed to generate stage-aware, high-performance kernels for
the emerging RVV extension [44]. It directly confronts the performance artifacts introduced by
quantization schemes–such as memory discontinuities–which are often overlooked by higher-level
optimization strategies.
6.2
Automated Kernel Tuning Frameworks
The automated generation of high-performance code for deep learning is a well-established field.
Frameworks like Halide [38] pioneered the decoupling of algorithm logic from its execution schedule,
allowing for powerful transformations. Subsequent systems like TVM [10] and its successor Ansor
[47] introduced domain-specific languages and sophisticated search strategies, including machine
learning-based cost models, to navigate the vast space of possible loop transformations [32] (tiling,
fusion, reordering) for generating efficient code on diverse hardware backends like GPUs and CPUs.
Unlike traditional frameworks (e.g., TVM, cuBLAS) that employ size-based kernel dispatch–selecting
implementations based purely on problem dimensions (𝑀× 𝑁× 𝐾) to optimize cache locality–
VectorWeaver adopts a stage-aware approach. Stage-awareness accounts for computational context
beyond data size: LLM inference’s Prefill and Decode stages differ fundamentally in arithmetic
intensity, memory access patterns, and microarchitectural overhead (e.g., vsetvli latency, tail loop
dominance), even when processing identical sequence lengths.
However, these frameworks typically operate at a higher level of abstraction. They primarily
focus on optimizing loop nests and rely on a general-purpose backend compiler (e.g., LLVM [23])
for the final instruction selection and micro-architecture-specific code generation. This dependency
can obscure low-level performance opportunities and bottlenecks. VectorWeaver differs from this
paradigm in three fundamental aspects:
Direct Assembly Generation: Instead of relying on a compiler backend, VectorWeaver generates
explicit RVV assembly. This provides fine-grained control over instruction scheduling, register
allocation, and software pipelining, enabling it to exploit architectural nuances that are often
inaccessible to a general-purpose compiler. Domain-Specific Primitives: It incorporates domain-
specific optimization strategies, such as our proposed “Width Expansion,” which are designed to
solve concrete problems that are invisible at the level of abstract loop transformations. Stage-aware
Specialization: Its performance model and optimization workflow are explicitly designed to be
stage-aware. This is a critical feature for the biphasic nature of LLM inference, which is not a
primary consideration in general-purpose tuning frameworks that typically optimize for a single,
static computational pattern.

This article introduced VectorWeaver, an automated framework designed to generate high-
performance, stage-aware LLM inference kernels for the RISC-V architecture. We identified critical
performance bottlenecks in existing frameworks stemming from quantization data layouts and the
divergent computational profiles of the Prefill and Decode stages. To address these, we proposed
